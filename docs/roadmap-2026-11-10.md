## Priority order (highest → lowest certainty / risk)

### 1. MIDI FX Rack (C3) — architectural debt / blocker
- **What**: `DeviceKind::Container` variant + Ctrl+G grouping devices into a rack; MIDI FX Rack that passes notes through the engine.
- **Status**: C1/C2 (Instrument + Audio FX Racks) are done (wave 1). C3 (MIDI FX Rack) is **blocked on the M9 note-path milestone** — the engine never calls `process()` on MIDI FX devices; they are UI‑hosted only. Until the note‑path refactor lands, a MIDI FX Rack cannot route MIDI to instruments.
- **Next step**: Defer C3 until the M9 note-path work is completed (see `docs/audit-2026-11-10-plugins.md` §5). No code should be started on C3 now.

### 2. Drop‑into‑launcher‑cell drag‑and‑drop — verified‑by‑test‑but‑broken‑live
- **What**: OS file drag‑and‑drop onto empty Clip Launcher cells should create audio clips via `launcher::add_audio` → `add_audio`.
- **Status**: Wave 2 added a regression test (`launcher_click_repaint_matches_full` / related drop tests) that passes in isolation, but **live behaviour is unchanged** — the drop does not land on cells. The code path exists (`app.rs:4784 App::drop_file` → `launcher.rs:1475` → `launcher.rs:2116` OS wire‑up), but the drop target registration for `Win::ClipLauncher` may be swallowed by the browser panel, or the cell hit‑test under the cursor does not run while dragging.
- **Next step**: Full runtime trace needed (not just unit tests). Audit the chain: OS drop → `Win::ClipLauncher` receive check → cell hit‑test under cursor → `drop_file` launcher‑cell branch → `add_audio`. Then fix the broken link. See user report and `todo.md` F1.

### 3. Launcher track polish — colour fill, volume/pan faders, header controls matching playlist
- **What**: Launcher tracks should look and behave like playlist tracks: full colour fill on headers, volume fader, pan fader, same header controls (mute/solo/etc.).
- **Status**: User reported all four sub‑items after testing `fd73cb54`. The track model (`os-model`) and mixer (`os-dsp`/`os-engine`) already support volume/pan on playlist tracks; the launcher just doesn't expose them. Audit needed: where the launcher track header is rendered (`views/launcher.rs`), what control set it already has, and how to wire the existing model fields.
- **Next step**: Short audit (file:line refs in `views/launcher.rs`, `mixer.rs`, `playlist.rs` header code) → then implement the four sub‑items (colour fill, volume fader, pan fader, header controls). See `todo.md` F2‑F4.
