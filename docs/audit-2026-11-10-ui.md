# Lemon Studio — UI Layer Audit (2026-11-10)

Generated from codebase audit using `cargo test`, targeted `read_file`/`terminal` reads, and the wave‑1/+2 committed code (`f42195de`, `fd73cb54`). All file:line anchors reference those commits.

## 1. Drawing / paint model

- **Canvas** (`crates/os-ui/src/glyph.rs`, `crates/os-ui/src/text.rs`): CPU canvas that every view renders into. Uses `tiny-skia` under the hood (os-ui crate).
- **`invalidate()` / `keep()` / partial‑repaint**: The core repaint cycle lives in `views/mod.rs`. `invalidate()` marks a window/region as needing redraw. `keep()` preserves a region across repaints. The `set_cover` promise (see `views/mod.rs` `set_cover` implementation) says a region will be fully repainted if any part is invalidated — but this is broken when `invalidate()` is called *full* (as the launcher and clipboard do on view switch).
- **Paint order** (`views/mod.rs` orchestration): windows are painted in this order: `Swallow`, `WinDrag`, `MinWin`, `MaxWin`, `CloseWin`, `PlArrangement`, `PlOptions`, `PlSnap`, `PlTool` (Draw, Paint, Delete, Mute, Slip, Slice). The toolbar (`PlTool(Draw)`) paints *after* the windows, which is why a full `invalidate()` covers it over — hover‑triggered partial paint restores it (the auditor's #1 suspect).
- **Popups / overlays** (`views::playlist::paint_overlays` at `browser.rs:637`, `:44`): browser context menus share `s.playlist.popup` and are painted after the browser part (`views/mod.rs:203`). The z‑order is actually correct (popup painted after), but partial‑repaint/keep interaction + the overlay paint being gated/duplicated across four call sites (`settings.open`, `over_dialog`, stale `overlay_on`) causes the menu to appear behind in practice. Fix: single unconditional popup‑paint site + `overlay_on` lifecycle cleanup + regression test `browser_menu_survives_launcher_repaints`.
- **Floating windows / dock / `Win::*`**: `device_rack_float` (`device_rack.rs:436/450`) tracks which devices are floated. `RackAct::PopOut(key)` / `Dock(key)` toggle them. A container tile's wrench opens the docked `Win::Container` list instead of the floating‑plugin machinery (its UI isn't a hosted plugin window).

## 2. Input routing

- **Hit‑test system**: each view has a hit‑test region; `views/mod.rs` computes `Part.area` vs `Seg::Toolbar` etc. The launcher issues a full `invalidate()` on every click, which resets the hit‑test region and causes the toolbar to disappear — the fix is to do partial repaints that preserve the toolbar's `keep` region.
- **Mouse event flow**: `mousedown` → hit-test → drag‑start (if applicable) → `drag` → `drop` → `click`. Double‑click is `mousedown` + `mouseup` within the same cell + time threshold; if the cursor is over the same hit‑test region, it's counted as a double‑click.
- **Drag & drop (internal + OS file drops)**: internal drags use the `drag` protocol in the view system. OS file drops go through `app.rs::drop_file` (`:4784`) → `launcher::add_audio` (`launcher.rs:1475`). The drop is wired at `launcher.rs:2116` (`app.drop_file(...)`), but live behaviour still has the cell‑don't‑land bug (re‑audit needed — the drop target registration for `Win::ClipLauncher` may be swallowed by the browser panel).
- **Double‑click handling**: pattern‑clip double click opens the piano roll (well‑established). Audio‑clip double click should open Tesla in the rack area (plan item F2, not yet audited for live behaviour).

## 3. Keyboard handling + shortcut map

Dispatch order (first to win):
1. **Rack keyboard block** (`app.rs:7969‑8008`) — Ctrl+D duplicate device, Ctrl+X/V cut/paste, SelectTile, PopOut/Dock, RemoveDevice. Runs *before* playlist::key.
2. **`playlist::key`** (`playlist.rs`) — Ctrl+T new track, Ctrl+Shift+T duplicate track, Delete clip delete, Tab view switch, Shift+wheel track movement.
3. **Global Cmd shortcuts** — Tab (switch between playlist/launcher/device rack), Ctrl+Tab (cycle views).

**Full shortcut map (as currently bound, verified from app.rs + playlist.rs + device_rack.rs):**
- `Tab` → switch focus (playlist ↔ launcher ↔ device rack)
- `Ctrl+T` → new track (via `track_links::insert_linear`)
- `Ctrl+Shift+T` → duplicate track
- `Ctrl+D` → duplicate selected device (rack) / duplicate track (playlist, but broken for launcher tracks — see A2 fix)
- `Delete` → delete clips (playlist); `Cmd::DeleteTracks` needed for selected tracks (D1, committed)
- `Shift+Wheel` → scroll within view; in playlist, also moves anchored track block (plan D2)
- `Ctrl+G` → group selected tracks/devices (D3, committed)
- `Alt+G` → ungroup (D3, committed)
- `Shift+G` → clip grouping (existing, not changed)
- `Ctrl+Shift+T` / `Ctrl+T` → track creation paths (different: Ctrl+Shift+T goes through control plane and creates a Track in launcher columns; Ctrl+D → `duplicate_tracks` only renumbers — see A2)
- `Ctrl+X` / `Ctrl+V` → cut/paste device (plan B1, wired in wave 1)
- `Ctrl+Shift+T` → new track (verified working in launcher)

## 5. Theming

- **`os-theme`** crate: theme tokens (colours, fonts), HSL adjustment model. Defines the dark theme used everywhere.
- **`.flstheme` files** (`crates/os-theme/themes/`): 21 theme definitions (Cinnamon Light, Graphite, Jade, etc.). Colours are HSL-based; the dark theme matches the app's overall aesthetic.
- **`os-ui`**: renders using `tiny-skia` + `fontdue` for fonts (Barlow + Cuprum). Theme colours come through `os-theme` tokens.

## 6. Text / fonts / icons

- **Fonts**: Barlow (weight variants) + Cuprum, loaded via `os-ui`. Used for all UI text — track names, plugin names, knob labels, shortcut badges.
- **Icons**: `crates/os-ui/icons/` (Tabler Icons set). Rendered through `os-ui` glyph pipeline.
- **`os-ui/src/kit/`**: kit module with reusable components (buttons, knobs, menus) that both the views and the plugin editors (os-plugkit) consume.

## 7. UI patterns to follow when adding new controls

**End‑to‑end template: adding a volume fader to launcher tracks** (the pattern to replicate from playlist):
1. Add the fader control to the launcher track header layout (`views/launcher.rs`).
2. Hook the control's value into the `Track.volume` field in `os-model` (or a derived `LauncherTrack` struct).
3. Wire the control's `ValueChanged` event to `app.rs` command `Cmd::SetTrackVolume` (or directly mutate the model if the command layer already supports it — check `app.rs` for existing `SetTrack*` commands).
4. Ensure the fader respects the track colour (use `os-theme` token for the thumb colour).
5. Add a test in `playlist.rs` style (e.g. `playlist::tests::track_volume_fader`) and replicate the same pattern in `launcher.rs` tests.
6. Verify that `invalidate()` uses `keep()` so the fader survives full repaints.

**Fragility list (UI‑layer–specific):**
- Full `invalidate()` on view switch covers the toolbar (E2) and resets hit‑test regions (launcher cell click).
- Popup menus duplicated across four call sites (E1) — need single unconditional site.
- Launcher missing `window_body` swallow hit that playlist has (incidental, noted in E1 audit).
- Size/fit check in `rack_ui.rs` causes some plugins (Lemon Delay) to fall back to generic dock.
